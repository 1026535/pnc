# C — Make live development a short feedback loop with a supported harness

Goal: new UI facts and routine corrections should not require rebuilding a private test driver or passing through the whole acceptance pipeline at every step. Final acceptance still proves the real changed production behavior on a bound candidate.

## Diagnosed cause and current policy

The frozen live030 package contains a 1,779-line case layer, 3,132-line driver, 347-line input boundary and 2,595-line fake-test file under ignored `.local-data/`. It repeats case selection, effect/control scope and reporting metadata; inherited case/count errors have already reached handback. These files contain useful working code, but ignored copied drivers are a costly place to maintain reusable testing capability.

The menu gap is structural: public entry requires reviewed destination/return, but discovery needs the native menu before those contracts can be authored. `locate_building` already solves passive acquisition; popup dismissal is not a task-owned menu action API. Repeated custom bypass preparation is the avoidable part.

Canonical live policy already says “smallest relevant offline group or affected selection,” reuse identity while continuity holds, batch compatible cases, continue independent cases after recoverable interruptions and retain unchanged proof. A blanket full gate before every discovery, every-building replay or every-case identity workflow is assignment overreach, not a current canonical requirement. The published non-Main resource policy already removes the old collection permission hold. Do not propose those completed policy changes again.

## C1 — Separate three purposes in the existing assignment contract

| Purpose | Entry gate | Permitted work and result | Completion boundary |
|---|---|---|---|
| Discovery | Reviewed relevant capture/action primitives, focused preflight, exact target/scope and candidate/helper binding | Acquire missing native UI facts; a new task-owned menu may be a successful capture result | Evidence sufficient for the named decision, not a production-route pass |
| Development validation | Coherent source slice, practical regression and focused affected boundary checks | Test one hypothesis; return observations suitable for a supported correction | Feature checkpoint; broader final gate can follow when the candidate is coherent |
| Acceptance | Independent source review, required finished-candidate offline gate, clean integration candidate and curated case set | Execute actual public production boundaries with stable source | Reviewed endpoint/return and required effects prove only selected changed cases |

Make this a field in the existing batch/manifest, not three launchers. A discovery candidate can be clean/fingerprint-bound without first running every unrelated suite. Final source immutability remains required for delegated acceptance. Never call a manual discovery pass an automated public-route pass.

Actual input receipts and logical operation counts remain distinct.

2. Define a typed case with ID, purpose, existing production entry/capture operation, target/slot, preconditions, required postconditions and justified limits. ## C3 — Add the missing discovery boundary explicitly

The supported capture operation must retain a task-owned unknown menu without invoking `CoreRuntime.observe()`'s automatic interruption recovery. Expose the smallest canonical persisted single-capture/perception boundary; do not clone its private implementation. The existing executor rejects raw points on blocked/coordinate-only observations, so review the developmental measured-control contract at that boundary. Do not promote the ignored helper's policy interception/raw-session path. A successful initial discovery can stop with native menu evidence and no menu input.

After fresh qualified body acquisition, a discovery case may perform a frame-bound typed body action through the existing executor and retain the resulting menu/panel. It can stop successfully at the unknown menu. A subsequent reviewed developmental control action must reference a fresh same-instance frame, identified task-owned control bounds, intended effect, receipt and immediate reobservation. When the control is ambiguous or the frame stale, capture and stop.

Prefer a typed measured selector once native evidence exists. If a one-shot manually identified control is needed during discovery, give it a separate developmental action contract and classification; do not reuse generic popup recovery, allow guessed coordinates or expose raw actuator access to feature workflows. This extension must be explicitly specified in the approved development assignment and reviewed by the existing action/provenance owner. Final route validation must use the implemented production selector/route afterward.

Keep production `open_building`'s reviewed-route admission intact. Discovery is a different supported test use case, not a success-shaped fallback after public admission refuses. This distinction removes the bootstrap obstruction without weakening production behavior.

## C4 — Keep routine development fixes with one owner, freeze for acceptance

The current `devin-live-test` contract prohibits source edits. Preserve that mode for acceptance. For development, propose a phase-aware contract using the existing implementation/live skills: one assigned implementation owner may diagnose and make a bounded in-scope correction after the live phase ends and its processes/task leases are released, run focused offline checks, freeze the new candidate, and request/run the next authorized changed-boundary phase. Same owner/context is useful; simultaneous source mutation and live execution is not.

The coordinator supplies scope and reviews the final package; routine crop annotation, fixture inventory and supported local corrections need not each create a new owner handoff. A second uncertain hypothesis or shared-contract redesign returns to the lead. Do not repeatedly invoke the 20-minute emergency lead checkpoint as the normal process. Pilot this mode on one concrete route-development package, with final independent acceptance unchanged. This is a proposed workflow amendment, not permission to violate a currently assigned immutable live-only brief.

## C5 — Match proof to changed boundaries

Maintain retained passing cases plus an explicit invalidation list. Rerun a case for changed code/assets/contracts or relevant environment/config/build variation affecting it; a new unrelated SHA alone is insufficient. Native fixture matching, projection math and documented transient loading sequences belong offline. Live proof establishes actual input→UI transition, timing/continuity and the final public route. Retain a small real publisher-contract suite; no blanket two-publisher replay of every pure geometry case.

A changed shared dispatcher can invalidate several routes; document why and batch representative/distinct required cases. Do not claim a dependency fingerprint proves independence when ownership is unknown. Keep final target identity, role, lease, fresh actions, actual postconditions, Main protection and uncertain-input stop rules.

## Pilot validation and success measure

Before live use, run existing/new harness fakes for selection, stale-frame/unknown control refusal, candidate/config preflight, receipt counts, scoped policy and cleanup. Run affected selection for tracked harness changes. Use one already-needed authorized non-Main development batch to prove actual canonical lease/receipt/cleanup behavior; do not add a live trip solely for report formatting.

Compare the next similar package with saved baselines using 13: helper preparation edits, owner handoffs, repeated setup/cases, time from useful discovery to a qualified candidate, coordinator repair and accepted routes. Record if the development mode reduces handoffs; do not claim a percentage from one pilot. Stop expansion if it adds another policy implementation or produces weaker evidence. No relaxed identity/lease/receipt guard is a performance target.
