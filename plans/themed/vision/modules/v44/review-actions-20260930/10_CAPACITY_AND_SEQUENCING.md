# E — Reduce queue delay and accept useful slices independently

Priority: coordinator practice now; any broader V44-first exception is a separately stated sequencing proposal. Owners: existing V/M/PW coordinators; no new scheduler. Review coverage: §4D; §5 additional agent and early downstream consumption; §7 sequencing.

## Cause and intervention

Shared CPU/live capacity is a real constraint, but a whole-epic gate can amplify a single local unknown into delay for unrelated ready work. Extra workers do not remove a shared integration/review queue. Conversely, a strict “one heavy job” label should not prohibit independent light analysis or justified compatible execution merely by habit. Keep resource decisions based on observed workload and explicit ownership.

Define the smallest independently useful acceptance slice by shared contract and actual dependency, rather than one building per worker or all 54 slots at once. Group a route's body/menu/destination/return when its evidence is ready; split unknown discovery from stable implementation when those have different inputs. A pending optional/externally owned case must not silently enter the gate for an otherwise accepted slice. Whole-V44 completion remains a separate accurate disposition.

### E1 — Work-in-progress and gate ownership

For the host-constrained lane, keep one running heavy batch and one prepared next batch; additional active implementation requires a separate ready dependency and disjoint ownership. Treat this as a starting operating rule, adjust with 13's wait data and existing commitments rather than inventing a scheduler. Assign one owner to each gate, review and shared file integration. Review terminal acceptance-critical packages before creating more partially finished work.

Do not make all velocity improvements wait for whole-V44 closure: source/consumer analysis, schema design and owned fixture work can proceed independently where ownership/capacity permit. Their heavy validation still queues explicitly. Do not patch an in-flight acceptance candidate to absorb unrelated infrastructure work.

### E2 — A concrete sequencing exception proposal

Preserve the user's V44-first instruction during execution. If the ledger identifies a named downstream plan whose exact required route is already accepted and pushed, propose that specific plan's bounded preparation/implementation with its source ownership and CPU/live cost, while the unrelated V44 blocker remains open. Recommend the exception only if it can consume otherwise idle capacity or materially reduce its critical-path delay without competing with the V blocker. This is an explicit decision about priorities, not a declaration that V44 is complete.

Technical route acceptance, publication, whole-epic completion and permission to resume the broader queue must remain four distinct facts in 11. A generic suggestion to “parallelize more” is not a deliverable.

## Deliverables

1. **Use the existing shared allocation record.** Record current heavy owner, workload class, candidate/package, start/readiness time, terminal release trigger and next owner. CPU allocation is distinct from BlueStacks task lease/reservation authority; both must be satisfied for live execution. Do not infer release from silence, a stale PID, an elapsed clock window or a worker's unreviewed completion sentence.
2. **Keep a small ready backlog in the current V view.** Each item names evidence prerequisite, source ownership, required resource, next action and wait reason. Examples: saved Watchtower geometry review is light; native matcher replay, broad tests and live perception need the heavy window; fixture-rule source mapping can be light but its final full fallback cannot overlap the critical V run.
3. **Overlap only useful independent work.** During one heavy run, prepare next case selection, source review, saved-evidence curation and exact commands. Do not start another OCR/matcher/full-suite/live worker on the same host without an explicit compatible allocation. Return the heavy window promptly when no executable work is ready; retain lightweight preparation ownership.
4. **Allocate another implementation agent only from a ready package.** Require settled evidence/API inputs, disjoint symbols/target keys/fixtures, a task-owned checkout, named tests and acceptance owner. If all blockers are the same menu capture, shared fixture gate, live target or policy interface, another implementer cannot advance them. Record the actual ready package rather than expanding agent count as a goal. Existing user/skill delegation permissions still govern dispatch.
5. **Handle acceptance before redispatch.** On terminal handback, verify source/cleanup, review acceptance-critical evidence, resolve findings and update 11. Reuse the worker for the next eligible package when ownership/resources are free; do not idle solely waiting for unrelated work. Existing callbacks/waits are the continuation mechanism; no new automation or guaranteed-outage-recovery claim is part of this plan.
6. **Make any queue exception concrete.** Default remains V44 first. A proposed exception must name the dependent plan, required accepted/pushed route SHA, feature scope, source/CPU/live budget, and impact on pending V44 cases. Obtain a sequencing decision only if none already exists. Technical readiness alone does not silently change the queue.

## Acceptance

Observe the next ordinary batch transition rather than running a synthetic performance test:

- [ ] At most one declared heavy owner unless a specifically reviewed compatible arrangement exists.
- [ ] Every waiting package has an owner, reason and exact release trigger; obsolete waits clear when evidence arrives.
- [ ] Next light preparation is available before heavy release where inputs permit.
- [ ] An additional worker, if used, owns a concrete disjoint ready package.
- [ ] Downstream route availability is recorded separately from permission to resume that plan.
- [ ] Existing live leases, protected Main and keep-warm obligations remain respected.

Validation is a review of the allocation/brief/handback timestamps in 13. No benchmark, process termination, BlueStacks restart or unit/live suite is required to introduce this coordination change. Do not stop another task's workload merely to make the allocation table match.
