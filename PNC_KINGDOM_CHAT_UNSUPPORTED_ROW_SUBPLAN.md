# PNC Kingdom Chat Unsupported-Row Sub-Plan

## 1. Purpose

This document defines the bounded follow-up plan for the live Kingdom Chat monitor failure where the transcript parser produced unsupported rows and correctly blocked archive persistence.

It is intentionally separate from:

- [PNC_KINGDOM_CHAT_MONITOR_IMPLEMENTATION.md](/c:/Users/lebel/pnc/PNC_KINGDOM_CHAT_MONITOR_IMPLEMENTATION.md), which owns the overall monitor architecture,
- [PNC_KINGDOM_CHAT_MONITOR_REVIEW.md](/c:/Users/lebel/pnc/PNC_KINGDOM_CHAT_MONITOR_REVIEW.md), which reviews the first implementation slice,
- [PNC_CHAT_WORKFLOW_SUBPLAN.md](/c:/Users/lebel/pnc/PNC_CHAT_WORKFLOW_SUBPLAN.md), which owns reusable chat navigation and send-flow mechanics.

This file owns one parser-quality correction:

- the live Kingdom Chat transcript parser must become robust enough to interpret normal visible chat rows without collapsing into unsupported fragments,
- while still failing fast on truly ambiguous OCR that cannot be archived safely.

Those strings are not inherently invalid sender formats. They are normal player-label fragments that became unsupported only because OCR failed to keep the corresponding message content attached to the same visible row.

That means the task's fail-fast gate is working, but the upstream transcript interpretation is still too brittle for the live screen variant.

## 1.2 Clarified visible row taxonomy

Additional screenshot review clarifies that the live Kingdom Chat surface contains multiple visually overlapping row families.

- Autogenerated event broadcasts can reuse the normal player avatar/name layout and the blue player-style bubble. For the monitor's current archive contract, those rows should still be treated as supported archivable chat because they appear as normal chat-bubble rows in the stream. Current examples include recruit, loot, and crafting lines such as `I obtained legendary hero ... (Tap to Join)`, `I got ... in Maze Treasure! (Tap to View)`, and `I crafted ... (Tap to view)`.
- Real player chat can include an orange bracketed title prefix before the sender name, and that title can change the bubble color to green or purple. Those rows are still `PLAYER` chat and should remain archivable.
- Normal player sender labels can follow the shape `[title optional][alliance tag optional]player name`, where the title is the yellow bracketed prefix, the alliance tag is the white bracketed prefix, and either prefix may be absent.
- Brown `System Message` rows are canonical `ANNOUNCEMENT` rows.
- Blue-bubble rows from names such as `Admin` should not be treated as real system/admin messages solely because of the displayed name; if they use the normal player-style row chrome, they stay in the archivable bucket.

For the current bounded monitor, archive eligibility should follow the supported visible row family, not authorship. In practice that means standard avatar-plus-name-plus-bubble rows remain in the existing archivable `PLAYER` bucket even when the text is autogenerated, while brown `System Message` rows remain `ANNOUNCEMENT`.

## 1.3 Scroll-state and clipped-row evidence

Additional screenshot comparison indicates that at least part of the March 24, 2026 failure surface is caused by scroll state rather than sender-format ambiguity.

- One screenshot shows a row where only the sender header is still visible near the bottom of the viewport while the message bubble is clipped by the lower chat chrome.
- A second screenshot of the same nearby region, after a slight scroll change, shows the full sender-plus-message row and becomes straightforwardly parseable.

That means the parser currently treats some partially visible top/bottom boundary rows as if they were complete row candidates. Those clipped boundary fragments should not be interpreted the same way as fully visible interior rows.

## 1.4 Non-text and image-rendered message content

Some visible chat bubbles can contain content that is not reliably OCR-readable as normal text because parts of the message are rendered as pictures, emoji-like glyphs, or other image content.

- Inline non-text glyphs inside an otherwise readable message are not a separate archive problem if the surrounding text still gives one trustworthy `message_text`.
- Entire message bubbles whose content is effectively image-only are different: they are still normal chat rows visually, but the current transcript model needs an explicit text representation for them.

For this bounded parser-fix plan, image-rendered content should remain archivable through canonical placeholders instead of being silently collapsed to an empty string.

- Large image-only bubble content should archive as a generic placeholder such as `[sticker]`.
- Small emoji-only bubble content should archive as canonical placeholders such as `[eyes emoji]`, `[happy emoji]`, or another controlled vocabulary when the visual asset can be recognized confidently.
- When the parser can prove that a bubble contains emoji-like non-text content but cannot identify the exact one safely, it should use a conservative fallback placeholder such as `[emoji]` rather than inventing a specific meaning.

The kept screenshot remains the ground-truth visual artifact. The transcript placeholder is a deterministic textual proxy, not a claim that OCR recovered the original glyph verbatim.

## 2. Current problem

The current monitor architecture intentionally rejects unsupported transcript rows.

That is the right task-level policy because:

- the archive must not silently drop or invent player chat,
- ambiguous OCR should surface as a failure artifact instead of poisoning transcript history,
- task-local ignore rules would duplicate parser logic and make safety inconsistent.

The real problem is therefore in the vision layer:

- the parser currently projects OCR-backed chat rows too directly into final chat-entry meaning,
- there is no dedicated normalization pass for row fragments, duplicate sender headers, or split sender/message evidence,
- there is no explicit handling for top/bottom boundary rows that are only partially visible because the chat list is mid-scroll or clipped by the input area,
- a live row that should be interpretable can therefore degrade into one valid player row plus extra unsupported fragments.

If we "fix" this by teaching the task to ignore unsupported rows, we would weaken the core safety contract. The parser must improve instead.

## 3. Goals

- Keep one canonical parser/classifier for visible Kingdom Chat rows.
- Improve row grouping and normalization before final chat-entry classification.
- Support the known live row families where authored and autogenerated chat can share the same archivable bubble-row chrome.
- Handle scroll-state boundary clipping so partially visible edge rows do not poison otherwise valid snapshots.
- Archive image-only bubble content through explicit placeholders instead of pretending it produced normal readable text.
- Preserve fail-fast behavior when a row still cannot be interpreted safely.
- Avoid task-local heuristics or chat-monitor-only exceptions.
- Add deterministic regression coverage for the March 24, 2026 live failure shape.
- Re-run the live monitor on `please b gentle` and expect either success or a smaller, more precise unsupported failure surface.

## 4. Non-goals

- Silently ignoring unsupported rows inside `CollectKingdomChatTask`.
- Inventing message text for sender-only OCR.
- Implementing full scroll-back history recovery.
- Adding account-specific or alliance-tag-specific parsing exceptions.
- Adding a separate cleanup pass that removes already-archived rows based on text heuristics.
- Treating obviously clipped top/bottom edge fragments as if they were complete interior rows.
- Silently converting image-only message bubbles into empty transcript text.
- Converting stickers or custom in-game emoji into ad hoc ASCII emoticons.
- Relaxing archive safety just to make one live poll pass.

## 5. Core architectural decision

The canonical fix belongs in the transcript parsing pipeline, not in the task.

Recommended parser shape:

1. Raw OCR lines should first be grouped into one intermediate chat-row candidate model.
2. That normalization pass should own geometry-aware merging of sender and message fragments when there is exactly one safe interpretation.
3. Only normalized row candidates should then be classified into the existing final meanings:
   - `PLAYER`
   - `ANNOUNCEMENT`
   - `UNSUPPORTED`
4. `CollectKingdomChatTask` should remain strict and unchanged: if final unsupported rows still exist, the task must fail and refuse to archive.

This keeps one canonical implementation per concept:

- vision owns row normalization and classification,
- the chat-domain model owns typed chat meaning,
- the task owns archive safety, not OCR cleanup.

## 6. Recommended parser behavior

### 6.1 Add one normalization phase before classification

The parser should stop collapsing directly from OCR lines to final `ObservedChatEntry` results.

Instead, add one internal intermediate layer that can represent:

- the sender evidence seen for one candidate row,
- the message evidence seen for one candidate row,
- the contributing OCR lines and their ordering,
- whether the candidate was formed by one exact safe merge or remains ambiguous.

### 6.2 Merge only when the interpretation is exact

The normalization phase may merge fragments only when geometry and ordering prove one interpretation cleanly.

Examples of acceptable merges:

- sender line plus adjacent message line that clearly belong to the same visible row,
- sender-only player labels that match the normal `[title optional][alliance tag optional]player name` shape and can be attached to exactly one neighboring message block,
- duplicate sender fragment that is fully absorbed by a neighboring already-proven player row,
- split message continuation lines that belong to one visible player row.

Examples of acceptable boundary handling:

- a top or bottom edge fragment that is visibly clipped by the viewport and cannot be proven complete may be excluded from the current snapshot instead of becoming a hard failure,
- a boundary fragment may be merged only when there is exactly one safe neighboring attachment inside the same visible capture.

Examples that must remain unsupported:

- sender-only rows with no attributable message,
- message-only rows with no attributable sender,
- candidates that could attach to more than one neighboring row,
- interior rows that are not viewport-clipped yet still cannot be interpreted safely,
- image-only message bubbles whose content cannot even be classified at the coarse placeholder level,
- noisy OCR that still cannot prove whether the row is player chat or announcement content.

### 6.3 Keep announcement classification strict and keyed to the non-archivable system row family

This plan should preserve the review document's earlier direction:

- announcement classification must require real announcement evidence,
- unsupported content must not be silently downgraded into `ANNOUNCEMENT`.

That means the normalization pass should make player rows more robust without weakening the distinction between `ANNOUNCEMENT` and `UNSUPPORTED`.

Additional clarified requirements:

- A row must not become `ANNOUNCEMENT` just because its text looks autogenerated.
- A titled player row must not become `UNSUPPORTED` or `ANNOUNCEMENT` just because the sender label begins with an orange bracketed title and the bubble color changes to green or purple.
- A sender label must not become `UNSUPPORTED` merely because it begins with an optional alliance tag such as `[DMG]`, or with a title-plus-tag combination such as `[Ruler][RST]...`.
- Known autogenerated recruit/loot/craft broadcasts that appear in the standard player-style bubble row should remain in the archivable `PLAYER` bucket for this monitor.
- Brown `System Message` rows remain straightforward `ANNOUNCEMENT` evidence.
- A displayed name such as `Admin` is not sufficient announcement evidence when the row uses the standard player-style bubble layout.
- A boundary-clipped fragment near the top or bottom of the visible chat viewport must not automatically fail the heartbeat if the parser can prove it is only a partial row outside the trustworthy visible window.
- Image-only message content must not be archived as an empty string or invented text; it should archive as a canonical placeholder when recognized safely.
- The placeholder vocabulary should be explicit and controlled, for example `[sticker]`, `[emoji]`, `[eyes emoji]`, or `[happy emoji]`, rather than arbitrary OCR guesses or ASCII substitutions.

For the bounded slice, the orange title prefix may remain embedded inside the stored `sender_name` text. The parser does not need a separate typed title field unless a later feature genuinely requires one.
